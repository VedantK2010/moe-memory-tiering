Expert tiering
across HBM and CXL

Mixtral 8x7B holds  GB of expert weights but routes each token to only of its experts per layer. That is an invitation to demote the cold experts to CXL-attached memory — if a placement policy can keep the hot ones in HBM. We replayed real routing decisions (two layers × tokens, top-2) through an analytic HBM/CXL tier model whose DRAM energy per bit is measured with DRAMSim3.

Capacity bought with time

An expert fetch costs a time-to-first-byte plus the transfer itself, t = L + S/B. At Mixtral's  MB per expert the transfer term is everything: try the latency sliders and watch nothing move. Every access costs either one HBM fetch or one CXL fetch, so each curve below is a hit-rate curve rescaled — the model is two-valued.

Does placement intelligence actually pay?

"Less CXL is faster" is true whichever experts you pick, so it proves nothing. The honest test holds the budget fixed and asks whether ranking experts by demand beats an arbitrary choice. Against random placements per budget, the demand-ranked placement is faster at every non-trivial budget, by up to at of 8 slots.

What if migration isn't free?

Every LRU miss installs a  MB expert into HBM. Static placement never migrates. Charging a fraction of a full HBM write () per install penalises LRU alone, so there is a cost at which its advantage disappears.

LRU advantage over static as migration cost rises

Real traces top-2, 4 of 8

Why this matters for the recommendation. If LRU wins only when migration is free, the honest advice is static or periodic placement. Real systems overlap part of an install with compute, so the true factor sits somewhere between 0 and 1; the curve is reported rather than a single point.

More, smaller experts: harder, not easier

Modern MoE layers use far more, smaller experts (DeepSeek-V3: 256 experts, top-8). The intuition is that each token touches a smaller fraction of experts, so tiering gets easier. Holding the HBM budget as a fixed fraction of all experts,

Prefetching: a negative result

A decode token takes tens of milliseconds and a CXL expert fetch about five, so there is time to fetch the next token's expert early — if it can be predicted. An online Markov predictor, gated by confidence, was run on datasets in configurations.

Prefetching can only hide latency. A correct prefetch still moves the expert across the link, just earlier, and a wrong one moves it for nothing, so CXL traffic and energy can only go up. The hit-rate gain is an upper bound (a correct guess is assumed to hide the whole fetch). On a bandwidth-constrained expansion link the exchange rate is poor.

Method, and what it does not show

The simplifications below are load-bearing. Each is a place where a reader should discount a result, and each is something the next version of this work should close.

Analytic model
Latency comes from an analytic two-tier model, not a cycle-accurate simulation: an access costs L + S/B at HBM () or CXL (). DRAMSim3 supplies DRAM energy per bit only.
Bandwidth-bound
At  MB per expert the latency term is of a CXL fetch, so the CXL/HBM time ratio equals the bandwidth ratio. CXL's latency adder is invisible at expert granularity — a finding, but it means this is a bandwidth study.
Two-valued
Every access costs one HBM or one CXL fetch, so time and energy are exact linear functions of hit rate. Energy does not independently corroborate the latency result.
Per-access re-fetch
Each access is charged a full expert transfer. Real inference reads a resident expert at tile granularity, so absolute times are fetch times, not decode latencies. Comparisons between policies survive.
Latencies
HBM and CXL-side DRAM are idle DRAM read latencies (controller + device) measured with DRAMSim3; the CXL link adds a cited . None is an end-to-end load-to-use latency, and at expert granularity none moves a result.
Energy
DRAM energy per bit is measured with DRAMSim3 on HBM2 and on DDR4-3200 standing in for DDR5 (DRAMSim3 has no DDR5 configuration). The CXL link figure is cited, not simulated — — and every energy saving is re-computed across of link energy in 0x70. The DRAMSim3 trace is a scaled sample: 8 × 64 B reads per expert fetch, each fetch continuing through the expert.
Real traces
Two layers of allenai/analysis_mixtral, full top-2 routing. Expert popularity is domain-dependent, and the thesis is about workload shift.
Batch-1
Except in the batch-size study, every result is batch-1 decode.
Synthetic traces
Used where a controlled change is needed (shift, robustness, scalability, capacity sweep); calibrated to Mixtral's skew and locality, not measurements of other models.
One model family
All real measurements are Mixtral 8x7B. Whether the conclusions carry to 64–256-expert models is tested only synthetically.
